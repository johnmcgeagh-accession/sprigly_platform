What exists, and what the phasing actually turns on

  • The transport is ready. POST /api/plan/intake and POST /api/plan/agent both accept source: 'voice' with a sessionId. The draft surface’s own route, POST /api/plan/draft/apply, does not — it takes {op:'text', text} and nothing else, so voice-sourced draft input would be indistinguishable from typed on the ledger. One field; added to the spec’s gap list.
  • A browser-side transcription path already exists and is already wired. app/src/components/plan/useSpeechInput.ts drives the Web Speech API — no backend, final transcript chunks appended into an editable field — and IntakeCapture.tsx uses it today. It degrades properly: unsupported hides the mic, no-permission reports itself.
  • So “disabled until the pipeline lands” may be stricter than it needs to be. Reusing useSpeechInput on the draft surface is a move, not a build, and would make frame B real on any supporting browser. What the separate workstream buys is server-side transcription — better accuracy, works where the Web Speech API doesn’t, and keeps the audio rather than only its transcript. Flagged for the operator to choose; the mockups show the specified state as A and the alternative as B.
  • The app’s existing voice overlay (voice-fab in PlanMobile) states “Voice arrives in a later stage” over a non-functional mic. This sheet replaces it on the draft surface and gives the same promise a usable floor.
  • The example prompts are written, not recorded. No client-facing prompt copy exists in the repo to source them from. They are phrased to elicit the intents the classifier can actually route — launch, event, emphasis — rather than open-ended questions whose answers the contract cannot express.
