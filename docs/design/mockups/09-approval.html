Where the content comes from

  • The tally is the real arithmetic the shipped approval card already does: captions for every planned post, hooks for reels and carousels, a script per reel. Earl of East’s October is 1 reel, 2 carousels, 7 singles — so 10 / 3 / 1. On a thin month the zero rows are omitted rather than shown as “0 hooks”.
  • The honest-consequence copy is the shipped copy, kept verbatim because it was written to correct a lie: an earlier version told clients “after this the dates and formats are set for the month”, which is false — every post stays editable by date until its own date passes.
  • Frame C is constructed, and says so. The template path’s sentence is exactly what rationaleFor() emits for basis:'template', and “no formatEngagement, no pillarShare” is asserted by test in Build A §9 — which is why that card shows no engagement line and no posting time. But no live client has a recorded thin draft: the one thin-data client (sprigly) has zero ig_posts and has never been assembled.

Wiring

  • The counts need no new API. They are derived client-side from the planned posts already in memory — draft.beats, loaded by GET /api/plan/draft for the viewed cycle before this sheet can be opened. A pre-approval summary endpoint would be a second source for a number the client is already holding.
  • Generate it → POST /api/plan/draft/approve — no body, no options, no partial approval. Returns {approved, captionsQueued, hooksQueued, failed}. A second approval is rejected (already_approved 409) rather than quietly succeeding, because approval spends money and a silent second fan-out is worse than an explicit refusal.
  • After approval the surface navigates to /?cycle=<cycleId> so the client lands on the month they just approved rather than on whatever the date heuristic picks.
